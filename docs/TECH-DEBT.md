# 技术债清理提示词（TECH-DEBT）

> 投喂本文件驱动一次技术债清理会话。本文件只写**处理规则**；历次清理的执行记录在 `docs/TECH-DEBT-LOG.md` 台账，与本文件配套但互不掺杂。

## 目标

回答两个问题并落实修复：

1. **增量判定**：自基线以来的增量代码是否产生了新技术债？逐文件、分账本给出有/无结论。
2. **逐项处理**：按下方清单逐类处理；不在清单内的新债型，处理后在清单中补登记。

只还债，不顺手加功能。

## 基线与增量

基线优先级：用户指定 commit > 台账最近一条记录的 HEAD > `git log --grep=技术债` 最近一条 > 含本文件的首次提交。
增量面 = `git diff --stat <基线>..HEAD` + 未提交改动；活文档无论有无增量，都抽查与增量相关的表述。

## 处理规则

### 账本一 · 记录债（零运行时风险，当轮清）

文字记录与代码实况的漂移。判定通则：记录说的和代码做的不一致，或记录绑定了不该绑定的具体对象。

| # | 类别 | 检查点 | 判定 |
|---|---|---|---|
| A | 配置与示例 | `.env.example` 等示例值是否与代码默认值/适配器实况一致；示例是否绑定特定厂商或项目；代码实际读取的环境变量是否齐全、无多余 | 失真必改；示例中立，与代码默认值对齐 |
| B | 活文档表述 | README、CLAUDE.md、docs/ 顶层中与增量相关的目录结构、命令、依赖政策、平台兼容性、产品形态是否与实况一致 | 冲突即改；改表述不改事实记录 |
| C | 注释与日志 | 注释是否复述代码而非记录「为什么」；注释描述的行为是否仍存在；注释掉的代码残骸；脚本注释与运行日志写死的具体名称 | 过期/复述型删或重写为「为什么」；注释掉的代码整段删除；日志描述机制而非历史个案 |
| D | 测试夹具与物料 | 假数据是否用真实感样本（厂商键名、真实格式密钥）造成误导；fixtures 是否标注用途与防误提交说明 | 假数据显式化（TEST_ 前缀）；保留测试语义所需格式（如脱敏正则依赖的 `sk-`） |
| E | 结构登记 | 新增/删除的目录、文件、共享类型是否同步目录树、README 导航、架构图、`src/types.ts` | 新增即登记，删除即摘除，无悬空引用 |
| F | 状态表述 | 「占位实现」「尚未落地」是否已被实现推翻 | 占位表述随实现更新；已完成态验收记录不改写 |

### 账本二 · 代码债（分级别处置）

代码能跑，但每多改一处都在付利息。

| # | 类别 | 检查点 | 判定 |
|---|---|---|---|
| G | 冗余与残渣 | 复制粘贴逻辑块；死代码、未用 import/字段/导出；同一能力多套并存实现 | 删除或收敛为单一实现；同一职责只留一条代码路径 |
| H | 上帝类/屎山信号 | 单文件/单类多职责混杂（配置、IO、业务、编排）；超长函数深嵌套；全局可变状态多处直改；「改一处坏三处」 | 识别职责边界后拆分；无测试锚点不动刀 |
| I | 补丁式修改 | 临时 if/开关变量；复制粘贴兜底；吞错式 catch；绕过 bug 而非修复 bug 的过滤层 | 追溯根因重构，禁止补丁套补丁；同一问题复发 2–3 轮升级为架构议题 |
| J | 扩展性缺陷 | 硬编码（供应商/路径/阈值）；接口绑死实现、无法插入新实现；违反分层方向；IO 散落在 adapter/store 之外 | 标尺：「新增一种实现要改几处」；最小接口可收敛的当轮收敛，需重设计的立项 |
| K | 纪律逃逸 | 无理由 any；绕过目录约定加载器；绕过工具注册表直接执行 | 对齐 CLAUDE.md §4/§5/§6；逃逸点逐个收回 |
| L | 测试判别力 | 用例在改动前后都绿（无对照组）；断言只锁「返回了字符串」这类恒真性质；阈值类逻辑的夹具恒回零（如用量恒 0）使分支不可达 | 每条防护性用例须能指出「换回旧实现它变红」的对照；不可达分支补可达夹具，或显式标注为未覆盖 |

### 级别处置（代码债）

| 级别 | 特征 | 处置 |
|---|---|---|
| 轻 | 死代码、未用 import、小段重复 | 当轮清，验证后随批次交付 |
| 中 | 超长函数拆分、补丁回收、局部抽象收敛 | 登记独立任务，小步重构，每步构建与测试全绿 |
| 重 | 上帝类拆解、架构级重设计 | 不混入清理批次，立项走 plan → execute → review，明确验收标准与回归范围 |

### 通用原则

- **活文档必改，历史存档不改**：`docs/superpowers/` 及带日期的过程文档是快照，记录当时的决定与验收事实，不做主动改写。
- **示例中立**：示例与模板只描述机制与协议，不绑定单一供应商；举例用「如 X、Y、Z 等均可」的并列形式。
- **上新删旧**：改一处时清同类残留，禁止只改眼前撞见的那一处。
- **先锚点后动刀**：重构前必须有测试锚点，无则先补锚点。

## 验证与收尾

1. 动了代码：构建零报错 + selfcheck + 单测全绿；纯记录改动：关键词残留 grep 归零。
2. `git status` 改动集与清理声明一一对应，无悬空引用。
3. 在 `docs/TECH-DEBT-LOG.md` 台账追加一行（日期、基线、清理后 HEAD、范围与结果），作为下次基线。
