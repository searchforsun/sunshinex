# /init 提示词对标 CLAUDE.md 设计规格

> 目标：把 `/init` 从「四句任务契约」升级为「目标大纲 + 证据要求 + 写法要求」的完备任务书，使生成的 SUNSHINE.md 达到 CLAUDE.md 量级的项目事实密度，同时保持提示词跨项目通用、前缀缓存零击穿。

## 1. 问题

`src/harness/sunshine-init.ts` 目前只向模型交代四件事：落点路径、真实性底线、完善语义、收尾汇报。文件性质仅以一行四个示例词带过（项目定位、构建/测试方式、架构分层、关键编码约定），产出分区完全交由模型自由发挥。实测形态：本仓 SUNSHINE.md 仅 14 行（三节九条），而 `SUNSHINE.md` 的每一行都经 `ContextLoader` 全量注入到**每一轮** Agent 上下文。

结论：提示词的欠约束是「生成太简单」的直接根因，需按目标大纲重写。

### 2. 目标与非目标

**目标**

- 提示词给出 SUNSHINE.md 的目标大纲（推荐分区 + 每类须回答的事实 + 证据来源）作为覆盖口径，而非固定格式；分区命名、顺序与颗粒度按项目实况调整。
- 提示词明确写入质量要求与格式契约，使产出达到 CLAUDE.md 量级的项目事实密度（150–250 行区间）。
- 完善语义从「不整体推翻」收紧为「既有行一个字不动，只新增缺失的覆盖项」。
- 通用性、前缀缓存、零新装配面三条不变量不破。

**非目标（YAGNI 登记）**

- 两阶段（先勘察报告、再落笔）流程。
- `/init` 参数化（指定分区、指定深度、dry-run）。
- 产出后的自动校验器／评分器。
- 自动安装依赖或代跑构建。
- 按大纲改写既有行（与「逐行保留」冲突，用户已否决）。

### 3. 关键裁决

| # | 裁决 | 结论 |
|---|------|------|
| D1 | 与 CLAUDE.md 的关系 | 目标项目独立文档：SUNSHINE.md 面向「运行 sunshinex 的项目」，不是本仓 CLAUDE.md 的移植对象，也不以导入既有规范文件为默认形态 |
| D2 | 大纲口径 | 提示词列推荐分区大纲 + 每类须回答的事实 + 证据要求；大纲是覆盖口径、不是固定格式（分区名/顺序/颗粒度按项目实况调整）；无证据的分区整区省略 |
| D3 | 篇幅 | 完整对标 CLAUDE.md：150–250 行为目标区间，信息完备优先于 token 节省 |
| D4 | 完善语义 | 增量补缺最保守档：仅新增缺失的覆盖项，既有行（含非标准分区标题、缩进、列表符号）逐行原样保留，不删不改不重排 |
| D5 | 改造路线 | 方案 A 目标大纲（非模板即文档、非两阶段勘察） |
| D6 | 通用性 | 保持零生态专名（不出现任何包管理器／清单文件／框架名），现有钉子用例不动 |
| D7 | 防回退用例 | 不加条数／行数阈值钉子，靠人工审阅 |
| D8 | 产出语言 | 不配置、不写死、**不进提示词**——`SUNSHINE.md` 用中文还是英文由模型按当前项目文档风格自判；产品语言轴（界面＋提示词）仍由 `--language` 配置（CLAUDE.md §15） |

## 4. SUNSHINE.md 目标大纲

### 4.0 使用口径（大纲，不是格式）

- 下表是**覆盖口径**：规定「哪些事实不能缺席」，不规定分区名、顺序与颗粒度；模型按项目实况合并、拆分、改名或增补。
- 「须回答的事实」是验收面：能回答的都回答，答不了的不编造。
- 无证据支撑的分区整区省略；不为凑齐大纲而造分区、灌水。

### 4.1 A 档（有证据则必写，5 类）

| 分区 | 须回答的事实 | 证据来源 |
|------|--------------|----------|
| 项目概览 | 项目名、一句话定位、技术栈与运行时、当前阶段与主要子系统 | 依赖与脚本定义文件、入口文件、顶层目录 |
| 常用命令 | 安装、构建、测试、单测过滤、运行、静态检查、发布；每行可复制命令 + 何时使用 | 脚本定义段、任务配置文件、CI 配置 |
| 目录结构 | 关键路径树，每条一句职责；只列有意义的目录，不逐文件罗列 | 目录实况 |
| 架构约定 | 分层与依赖方向、模块边界接缝、数据与控制流、不可破的不变量 | 入口装配点、模块 import 关系 |
| 编码规范 | 语言与严格度、文件职责边界、错误处理约定、共享类型登记要求、依赖引入标准 | 配置文件、既有代码风格 |

### 4.2 B 档（有证据才写，无证据整区省略，7 类）

| 分区 | 触发条件 |
|------|----------|
| 验证与门禁 | 存在提交前检查组合、测试数据隔离等纪律 |
| 构建与发布 | 存在打包脚本、产物目录、分发渠道 |
| 运行与配置 | 存在环境变量或配置文件及其优先级链 |
| 扩展机制 | 存在插件／技能／工作流等目录约定与加载语义 |
| 平台与兼容 | 有平台差异、版本下限或已知限制 |
| 边界与约束 | 有禁止项、不可写区、外网或权限约束 |
| 压缩保留指令 | 有必须在上下文压缩中跨轮保留的约束（`## Compact Instructions` 区） |

### 4.3 写法要求（贯穿全篇）

- 一条一行，陈述句或祈使句，能被直接执行或据此判断。
- 有数字给数字（版本、端口、超时、上限），有路径给相对路径。
- 不写历史、计划、进度与「当前正在做什么」。
- 禁止通用最佳实践类空话（如「写清晰的代码」）——这是文档变水的主因。
- 不设语言与文体条款：产出语言（中文/英文）与文体由模型按当前项目自判（§8），提示词不写死、不设配置项。
- 禁止逐文件罗列与全量依赖版本表：会立刻过期且每轮占据注入预算，只写关键路径与接缝。
- 无证据支撑的内容宁缺勿编。
- 分区组织不设固定格式：不照搬大纲的分区名与顺序，按项目实况组织。

## 5. 提示词结构（七层）

| 层 | 内容 | 行数 |
|----|------|------|
| L1 任务与落点 | 分析当前代码库，生成／完善 SUNSHINE.md（落点绝对路径内嵌） | 1–2 |
| L2 文件性质 | 每轮注入 Agent 上下文的长期项目约定，**每行都在花 token**，只承载长期稳定事实 | 2–3 |
| L3 探索要求 | 落笔前必须实际读：依赖与脚本定义、入口文件、配置、目录实况、CI 配置；每条陈述须能追溯到读过的东西 | 2–3 |
| L4 目标大纲 | 4.1 的 A 档 + 4.2 的 B 档，每类列「须回答的事实」与证据来源，并明示「这是大纲、按项目实况调整」 | 16–22 |
| L5 写法与质量 | 4.3 全部条款 | 5–6 |
| L6 新建／完善分支 | 无文件→从零生成；已存在→先读全文、既有行不动、只补缺失覆盖项、合并写回 | 3–4 |
| L7 收尾 | 一句话汇报做了什么 | 1 |

**大纲以「须回答的事实」表述，不内嵌带填写提示的模板正文**——避免提示语（含 HTML 注释）残留进产出，这是选方案 A 而非「模板即文档」的原因；同时在大纲开头明示「这是大纲、按项目实况调整」，避免模型把分区名当固定格式照搬。

**格式契约**：要求以 `#` 分区组织（`ContextLoader` 与 `parseSunshinex` 按 `#` 标题切分区）；压缩保留区若使用，必须用精确标题 `## Compact Instructions` 或 `## 压缩指令`。

## 6. 完善语义与写回契约

`write` 工具为整体覆盖语义（无追加模式），「增量补缺」须靠「读全文 → 合并 → 单次写回完整内容」实现。

| 步骤 | 动作 | 硬约束 |
|------|------|--------|
| 1 | 读取全文，建立既有一级分区标题清单 | 未读全文不得落笔 |
| 2 | 对照目标大纲标记缺失的覆盖项 | 按既有标题与内容双重判断；已有分区不重建 |
| 3 | 对每个缺失覆盖项，按 L3 取证后补写 | 无证据则整区省略，不为凑齐大纲编造 |
| 4 | 合并为完整内容，**一次** `write` 覆盖 | 禁止分次写盘；禁止只写新增片段 |
| 5 | 汇报补齐了哪些覆盖项 | 按落盘事实汇报 |

**边界情形**

- 既有行逐行原样保留，含非标准分区标题、缩进与列表符号，不做风格重排。
- `@path` 导入行视为既有内容原样保留；若文件近乎只有导入行，则在导入行之后补齐运行期事实分区。
- 既有内容过期（如命令已变）不删不改；纠正既有事实归用户手工（D4 最保守档的代价）。
- 幂等：重复执行不产生重复分区、不重复追加同一事实。
- 审批被拒或任务中断时按落盘事实汇报，不虚报成功（沿用现状）。

## 7. SUNSHINE.md 既定机器消费者（分区标题须避让）

| 消费者 | 标题依赖 |
|--------|----------|
| `ContextLoader.collect` | `@path.md` 导入行展开（递归 ≤4 层） |
| `extractCompactInstructions` | `## Compact Instructions` / `## 压缩指令` 精确标题 |
| `parseMcpServers` | `## MCP 服务器` 分区，行式 `name \| endpoint [\| transport:… args…]` |
| `parseSunshinex`（selfcheck / perception） | 按 `#` 标题切分区；`规则/规范/rule/convention/编码/安全` 标题下的 `-`／`*` 行计为规则；`项目名称` 首行作项目名；`架构原则` 为架构条目 |

推论：模型若填入上述分区，必须使用精确标题与行式格式；大纲不强制模型编造这些分区（MCP 与压缩保留区仅在有对应需求时写）。

## 8. 通用性、语言轴与不变量

- **通用性**：提示词不假设语言、框架、包管理器；证据要求统一表述为「项目的依赖与脚本定义文件」等生态中性措辞，不出现包管理器／清单文件／框架专名（D6，现有 `! /package\.json/` 钉子不动）。
- **两条语言轴（对齐 CLAUDE.md §15）**：①项目语言轴=产品自身提示词与界面文案的语言，由 `--language=en|zh` 配置，`/init` 提示词沿用 `pick(en, zh)` 双语同步重写（不逐字直译、不用两个语言轴互相替代）；②产出语言轴=`SUNSHINE.md` 写中文还是英文，**不由提示词规定、不设配置项**，模型按当前项目既有文档风格自判（中文项目写中文、英文项目写英文）。据此**撤销早先「提示词写入产出语言条款」的设计**：可自判的事不该写死成硬约束，提示词侧只承担「不设条款」这一事实本身。
- **机器消费区例外**：`## Compact Instructions` / `## 压缩指令` 等精确字面按既有约定书写，仅在需求存在时写。
- **前缀缓存零击穿**：`/init` 提示词经 fork 注入（`src/tui/session.ts` 的 `runTaskFlow` 走 `scope: 'fork'` + `seedHistory`），大纲全文落在 fork 尾追、不进主链、不动稳定段——这是大纲可以写长的前提。
- **零新装配面**：不改 `sunshineInitGoal(root: string, exists: boolean): string` 签名，不新增工具，不改调用点（`session.ts` `/init` 分支），仅扩提示词正文 + 测试 + 手册文案。

## 9. 验收矩阵

1. **新建语义**：`sunshineInitGoal(dir, false)` 输出含 A 档 5 类覆盖事实、B 档 7 类触发条件、「大纲非固定格式、按项目实况调整」的口径声明、落点绝对路径、真实性底线、写法要求条款。
2. **完善语义**：`sunshineInitGoal(dir, true)` 输出含「先读全文、既有行不动、只补缺失覆盖项、单次整体写回」四项约束。
3. **通用性钉子（既有用例）**：提示词不出现生态专名（`package.json` 等）。
4. **零模板残留**：提示词不含 HTML 注释式填写提示；产出契约明确禁止 `TODO`／占位符。
5. **既有英文锚点存活**：`refine` / `from scratch` / `as-is` / `wholesale` / `never fabricate` 仍在（现有 5 个断言不改）。
6. **产出语言反向钉子**：提示词中不得出现产出语言指定或「按项目语言写成英文/中文」类条款（en／zh 两侧同断言）——产出语言由模型自判（§8、CLAUDE.md §15）。
7. **门禁**：`tsc` strict 零报错、全量测试绿、`selfcheck` OK。
8. **前缀回归**：既有前缀稳定与 fork 首帧连续用例全绿（本改动不动装配面，期望零影响）。
9. **手册同步**：TUI-MANUAL 的 `/init` 行与数据目录段对 SUNSHINE.md 的描述与「大纲 + 增量补缺」口径一致。

## 11. 风险与回退

- **产出灌水**：模型为凑篇幅写空话——由 4.3 禁止性条款与「无证据宁缺勿编」约束；无阈值钉子（D7），风险由人工审阅兜。
- **提示词过长**：约 30–45 行的提示词经 fork 注入，不进主链、不参与前缀缓存命中面，无 token 累积效应（七层合计见 §5）。
- **回退**：改动集中在单文件提示词与测试，回退即整体还原该文件。
